How TrailMix fits together

A tour of the whole codebase for someone who knows how to build software but hasn't read this repo yet. It goes outside-in: what the tool does, which processes run, how one command moves through them, and then each language layer in turn.

Go CLI, recorder daemon, transcription, navigation   Swift native audio capture   Lua Neovim companion   External tmux, OpenAI, OpenCode

01What it does

Start with the user's view. Every design choice below follows from it.

You press a hotkey bound to trailmix toggle. TrailMix then:

  1. Creates a dated Markdown note, e.g. ~/Documents/TrailMix/2026-09-30/16-01-38.md, stamped with a hidden <!-- trailmix: meeting <id> --> marker.
  2. Starts recording two tracks: your microphone and the system's audio (the other people on the call).
  3. Streams both tracks to OpenAI's realtime transcription API while still writing the full audio to local disk.
  4. Opens the note in Neovim, inside a tmux session for the day, and brings that terminal window to the front.

While you type notes, the Neovim plugin lets you drop @MM:SS timestamps, open a live transcript split, and ask an AI assistant questions. Answers cite the transcript passages they rely on. Pressing the hotkey again stops the recording.

02The four processes

The most useful mental model: during a meeting, four of our own processes are alive at once, and they talk only through pipes, a Unix socket, JSON on stdout, and files.

Go

① CLI and ② recorder are the same binary

The CLI launches the daemon by re-executing itself with the hidden subcommand _record, in a new session (Setsid) so it survives the terminal closing. The daemon then holds a lock and serves status/stop over recorder.sock.

Swift

③ is a separate signed .app

Go can't easily call ScreenCaptureKit, and macOS attributes Microphone / Screen Recording permissions to an app bundle. So capture lives in a small Swift program the recorder spawns as a child.

The CLI finds the helper relative to its own resolved path (recorder.go: config()):

Why the helper's config is trackedThe Makefile writes .build/helper-config containing the arch list and version, and forces a Swift rebuild when it changes. File mtimes can't tell you "this was built for a different architecture."

05Trace: trailmix start

Following one command end to end covers most of the Go code. toggle is start when idle and stop otherwise.

The dispatch entry point

cli.go: Run is a flat switch. Commands that change lifecycle state first take workspace.lock so two hotkey presses can't race:

switch args[0] {
case "start", "record", "toggle", "open", "stop":
    guard, err := lifecycleLock(p)   // flock, waits up to 50s
    defer guard.Close()
}
switch args[0] {
case "start", "toggle", "open": return workspace(p, args[0])
case "record", "_record":        return recordCommand(p, args)  // _record → serve()
case "status", "stop":           return statusCommand(p, args)
case "transcript", "retry":      return transcriptCommand(p, args)
case "ask", "answers":           return runAnswers(p, args[0], args[1:])
...

The daemon's core loop (recorder.go: capture)

The daemon spawns the Swift helper, then reads one JSON event per line from its stdout and folds each into the session status. Pseudocode:

cmd := exec(helper, "record", "--output", dir, "--mic", mic, "--stream", "true")
go func() {               // stop path
    <-s.stop                  // closed by socket "stop", SIGTERM, or 3h timer
    stdin.Close()             // helper reads EOF → finalizes files → exits
    after 10s: kill
}()
for line := range stdout {
    switch event.Type {
    case "started":  state = "recording"; read capture.json for actual mic name
    case "progress", "stopped": update elapsed + per-track stats
    case "error":    remember error
    case "transcription_error": transcriber.Fail(...)
    }
    saveStatus()              // atomic write of session.json + last.json
    indicator.publish()       // async tmux status-line update
}
Stop is just closing a pipeThe helper treats stdin EOF as "stop", so if the Go daemon crashes, the OS closes the pipe and the helper still finalizes its audio files cleanly. The same idea runs the other way: if the helper's stdout write fails, it stops itself instead of recording invisibly.

How status and stop find the daemon

// client.go: tiny request/response over a Unix socket
conn := net.Dial("unix", "~/Library/Application Support/TrailMix/recorder.sock")
send {"command": "status"}     // or "stop": daemon blocks until finalized, then replies
read status JSON
// No socket? → lastStatus(): read last.json. If it says "recording" but nobody
// holds recorder.lock, report state "interrupted" (the daemon died).

06Swift capture helper

One file, native/Capture.swift. You can read it as four classes and a main.

PieceRole
CaptureMain.mainSubcommands: devices, permissions, record, prepare-stream, self-test. Errors become {"type":"error"} + exit 1.
CaptureMain.recordRequests mic access, picks the device, configures an SCStream for audio + microphone at 48 kHz (with a 2×2 px dummy video config, since ScreenCaptureKit requires a display filter), writes capture.json, starts a 1 s progress timer, waits for a stop signal.
CaptureOutputThe SCStreamOutput delegate. Each sample buffer gets its timestamp converted to host-clock seconds since origin, then is routed to the system or microphone writer. All mutable state runs on one serial DispatchQueue.
TrackWriterPer track: writes original-format PCM to <track>.caf and one row per buffer to <track>.timeline.jsonl (file frame → meeting time, plus gaps). Tracks peak level for the "silent mic" warnings.
StreamWriterPer track: resamples to 24 kHz mono Int16 (what OpenAI wants) and appends to <track>.stream.pcm, publishing a row to <track>.stream.jsonl only after the bytes are written.
// The protocol to Go is just newline-delimited JSON on stdout.
func emit(_ value: [String: Any]) {
    outputLock.lock(); defer { outputLock.unlock() }
    guard !stdoutLost else { return }
    do { try FileHandle.standardOutput.write(contentsOf: jsonLine(value)) }
    catch { stdoutLost = true; onParentLost?() }  // parent gone → stop cleanly
}

// Stop sources all feed one AsyncStream: stdin EOF, SIGINT, SIGTERM, fatal errors.
Thread.detachNewThread { _ = readLine(); stops.continuation.yield(()) }
...
for await _ in stops.stream { break }
try await stream.stopCapture()
try output.finish()   // close CAF headers, fsync journals, emit "stopped"
Two copies of the audio, on purposeThe .caf files are the authoritative recording in the original format. The .stream.pcm files are a durable queue for transcription. If the queue is lost or damaged, prepare-stream (used by trailmix retry) rebuilds it from the CAF + timeline, and refuses if the rebuilt bytes would differ from what earlier transcripts already reference.

08Transcription pipeline

The most intricate Go package. Its core rule, from the package doc: capture never calls into this package and never waits for the provider.

// stream.go: Runner.track(name), simplified
open timeline (.stream.jsonl) and audio (.stream.pcm)
for {
    line := read next row        // at EOF: if capture finished, flush and return; else wait and retry
    pcm  := read row.Bytes from audio at row.Offset
    seg.add(row, pcm)            // accumulates RMS energy, tracks silence
    ensureProvider()             // lazily connect; on failure mark track "degraded"
    provider.append(pcm)
    if seg.boundary() {         // ≥15s, or ≥0.1s with 0.6s of quiet
        turn := seg.take()
        store.saveTurn(turn)     // written BEFORE commit, so it can be retried
        provider.commit(turn)    // pad to 100ms if short; provider replies later with text
    }
    if session older than 55 min { drain and reconnect }
}

Passage IDs are deterministic (microphone-000000720368 = track + byte offset into the PCM queue), which is what lets trailmix retry replay only the turns that never received a final and dedupe against ones that did. Finish() gives in-flight network work at most 12 s after capture stops.

streamingdegradedinterrupted
A failed network never stops capture; the audio stays on disk.

submitted_seconds and estimated_usd per track in status.json.

transcription.Model in store.go; session config in provider.go: connect.

09What lands on disk

Three places. Knowing them makes debugging much easier: you can just cat the state.

# State: ~/Library/Application Support/TrailMix # (or $TRAILMIX_HOME) recorder.sock # daemon's socket recorder.lock # held by the live daemon workspace.lock # serializes lifecycle cmds last.json # last status snapshot latest-meeting.json # what `open` reopens meetings/<id>.json # note path, tmux target, # recording dir e-<rand>.sock # nvim --listen sockets launch-*.log # daemon startup logs recordings/<ts>-<n>/ # one per recording ↓
# A recording directory capture.json # mic id/name, clock origin capture.log # helper stderr session.json # recorder status meeting.json # meeting identity microphone.caf # original audio microphone.timeline.jsonl microphone.stream.pcm # 24k queue microphone.stream.jsonl system.* # same four for system answers/<answer-id>/ # prompt.txt, runner.json, # answer.json per question transcription/ status.json <track>-<offset>.turn.json <track>-<offset>.passage.json

And your notes: ~/Documents/TrailMix/YYYY-MM-DD/HH-MM-SS.md, with sidecars ….transcript.md (exported at stop) and ….answers.md (AI answers) beside them. Settings live separately in ~/.config/trailmix/settings.json, and the API key in its own credentials file under the same directory (auth.go).

10tmux & terminal navigation

internal/navigation gets your note on screen however TrailMix was launched: from inside tmux, from a hotkey with no terminal open, or with an editor already running.

  1. Find or create the editor pane. List every tmux pane and look for one tagged with pane options @trailmix_meeting = this ID and @trailmix_note = this path that is still running nvim. Tags are used because tmux numeric IDs get recycled and titles change.
  2. If missing, tmux new-session (first meeting of the day) or new-window into trailmix-YYYY-MM-DD, exec'ing nvim --listen <socket> -- note.md with TRAILMIX_CLI/TRAILMIX_HOME in its env. Then set the three pane tags.
  3. If the pane exists but nvim switched to another buffer, use its --listen socket to show the note again (showNote), keeping any unsaved text.
  4. Get it on screen. If a tmux client is attached, switch-client to the target. If not, run terminal.command (default: AppleScript to Terminal.app) with {tmux}/{target}/{dir} filled in, and wait up to 6 s for a client to attach.
  5. Focus. Walk the tmux client's process ancestry up to the terminal app, then focus via Aerospace (exact window) or macOS app activation.

Separately, indicator.go sets the tmux user option @trailmix_rec while recording, so a status-line snippet can call trailmix status --tmux to show ● 16:01. Updates go out on their own goroutine and only the latest state is kept, so a hung tmux can't slow capture.

11Neovim plugin (Lua)

The plugin is a thin client. It never talks to the daemon or OpenAI directly: everything goes through vim.system({cli, ...}) and parses the versioned JSON that comes back.

Timestamp insertion: a good example of the plugin's style

function M.add_timestamp()
  id     = note.id(buffer)                     -- must have exactly one marker
  tick, cursor = changedtick, cursor position  -- snapshot the editing target
  autocmd on CursorMoved/TextChanged/BufLeave → canceled = true
  vim.system({cli, "status"}, {timeout = 4000}, function(result)
    if canceled or tick/cursor/buffer changed then notify("canceled") return end
    state = cli.decode(result.stdout)
    require state.live, state.state == "recording", state.meeting_id == id
    require state.clock_age_seconds <= 5        -- don't stamp a stale clock
    insert "@MM:SS" (or "@HH:MM:SS") above cursor
  end)
end

The pattern: async call, and if anything changed while waiting, give up rather than guess. You'll see the same approach in the transcript refresh, which validates the whole snapshot before touching the buffer so a bad refresh leaves the previous transcript in place.

12Ask & citations

How a question in Neovim becomes a cited answer. This path crosses all three languages and an external AI tool.

  1. ask.lua pipes {"question", "notes", "note_path", "selection"} into trailmix ask --meeting ID.
  2. answers.go: ask checks that the note snapshot carries this meeting's marker, reads the finalized transcript, and builds a prompt: fixed instructions plus a JSON blob of notes and passages (questionPrompt).
  3. assistant.Run launches the configured command (default opencode run --format json --agent trailmix-ask) with the prompt on stdin, in its own process group, with a timeout and a 4 MiB output cap. For OpenCode it injects a deny-all agent with a random name, so the assistant can't run tools or edit files.
  4. The model is told to cite with [[passage:ID]]. citeAnswer rejects the answer if any cited ID isn't in the supplied evidence, then rewrites valid tokens into links like [04:12](trailmix://meetings/<id>/passages/<pid>).
  5. The answer is appended to the .answers.md sidecar beside the note, and the exact prompt, raw runner output, and an answer.json record are saved under answers/<answer-id>/ in the recording directory. The result goes back to Neovim as JSON. ask.lua shows it in the panel; gf on a link opens the transcript at that passage.
// answers.go: citations are validated, not trusted
answer := citationToken.ReplaceAllStringFunc(text, func(token) {

13Patterns you'll see everywhere

Once you recognize these, most of the "why is this so careful?" code makes sense. The codebase consistently assumes processes crash, users press hotkeys twice, and networks fail.

flock, not PID files
recorder.lock, workspace.lock, capture.lock, per-meeting .artifacts.lock. The kernel releases a flock when the process dies, so stale-lock cleanup is never needed.
Atomic writes
Write path.tmp, then rename. Readers never see half a JSON file (saveStatus, meeting.WriteJSON, atomicJSON).
Never overwrite
O_CREAT|O_EXCL for notes, recording dirs, CAF files, logs. Collisions get a suffix or an error; nothing gets clobbered.
Capture outranks everything
Transcription, tmux indicators, navigation, and editors can all fail while recording continues. Errors are surfaced as warnings / degraded states, not crashes.
Identity in the note
The <!-- trailmix: meeting ID --> marker is how every component (Go, Lua, sidecars) agrees which meeting a buffer belongs to, even after restarts or midnight.
Exec arrays, no shell
terminal.command and assistant.command are argv arrays with placeholder substitution. tmux is given multiple args so it execs directly with no shell parsing.
Secrets stay narrow
captureEnvironment() strips OPENAI_API_KEY from the helper's env; websocket errors redact the key.
Versioned JSON boundary
Every CLI JSON document goes through cliout; the plugin checks the version. Adding fields is fine; removing or changing meaning bumps it.

14Tests & CI

LayerHow it's tested
Go*_test.go beside each file, run with -race. transcription_test.go stands up a fake websocket server and writes synthetic PCM queues to test out-of-order finals, disconnects, retry dedupe, and session rollover. Recorder tests use a fake helper via TRAILMIX_CAPTURE_HELPER.
Swifttrailmix-capture self-test pushes real PCM buffers through TrackWriter/StreamWriter without opening devices or prompting for permissions.
Luanvim --headless -u NONE -l tests/nvim/*.lua with a stubbed CLI.
CI.github/workflows/ci.yml on macos-15: gofmt, go vet, go mod verify, make test. release.yml reruns CI on a tag, then make dist.
What tests can't coverReal permission prompts, real devices, and long real calls. The README is upfront that short trials work end to end and long meetings have seen little use, so that's where to expect surprises.

Hands-on tip

Run a short trailmix start, then in another shell: trailmix status | jq, ls "$(trailmix status | jq -r .directory)", and tail -f …/microphone.stream.jsonl. Watching the files grow while you talk shows the Swift → disk → Go hand-off directly.
